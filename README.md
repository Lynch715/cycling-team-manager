# 模拟自行车队经理

一款公路自行车队经理游戏的完整技术底座。技术无关：只依赖 Python 标准库
（美术工具额外用 Pillow），Unity / Godot / Web 前端都能把它当作数值服务调用。

---

## 安装

需要 Python 3.10 或更新版本，游戏本体不装任何第三方依赖。

```bash
git clone <仓库地址>
cd 模拟自行车队
python3 source/play.py
```

**美术资源单独下载。** 254 张图共约 640MB，超出 git 的合理承载，因此不在仓库里，
放在 [Releases](../../releases) 页面。下载 `模拟自行车队经理_完整美术资源_254张.zip`
后解压，使目录结构为：

```
模拟自行车队/
├── assets/art/01_riders/...
├── source/
└── data/
```

校验完整性（可选）：

```bash
shasum -a 256 -c 模拟自行车队经理_完整美术资源_254张.zip.sha256
```

不下载美术也能玩——界面会缺图，数值与流程完全不受影响。
命令行的那几个入口（`run_season.py` / `history.py` / `test_sim.py`）根本用不到美术。

`source/tools/` 里的美术处理脚本额外需要 Pillow：`pip install Pillow`。

## 先玩一局

```bash
python3 source/play.py
```

浏览器会自己打开。选一支队接手，定打法，逐场比赛跑下去，处理弹出来的
俱乐部事务，赛季结束后签人、集训，进入下一年。存档随时可以按。

**为什么是本地服务端，不是又一个静态 HTML。** 项目里那些 `原型_*.html`
都是把 Python 算好的结果冻进页面里——能看，不能玩。要真的能玩，游戏逻辑
必须在玩家点下按钮之后运行。三条路：把引擎移植成 JS（两套数值实现，早晚
不一致，这是最贵的错误）、预演所有分支（组合爆炸，而且玩家的选择就不再是
选择）、**让 Python 当数值服务**（引擎只有一份，前端只负责显示和收集输入）。

第三条顺带验证了这个项目一直宣称的架构：换成 Unity 或 Godot 前端时，
要换掉的只有 HTTP 之上的那一层。服务端只用标准库，只监听 127.0.0.1，
不装任何依赖——它是一个单机游戏的壳，不是一个 web 服务。

`python3 source/verify_play.py` 会脚本化地把这条路走一遍：选队 → 定打法 →
25 场比赛 → 弹出的事务 → 赛季结算 → 转会集训 → 第二个赛季 → 存读档，
中间任何一步返回 500 或者哪张图取不到，它就红。**这是第一个验证「能不能
玩下去」而不是「数值准不准」的东西**，第一次跑就抓出三个 bug：拍板赛季
打法会顺手把第一场比赛跑掉（玩家根本没机会看赛道）、退役车手的积分还留在
排行榜里导致休赛期之后整个界面 500、领奖台传的是逻辑图名而不是 URL。
这三个用数值测试一个都抓不到——因为命令行跑完赛季就不再序列化状态了，
而界面每一帧都要序列化。

## 三层结构

```
sim/         比赛怎么跑     —— 物理、能量、集团、战术。不认识"合同"和"年龄"
game/        世界长什么样   —— 车手档案、车队、赞助商、赛历、赛季、经营
tools/       生产管线       —— 美术盘点、回放导出、原型构建
```

分层的价值在于：数值平衡（sim）和玩法设计（game）可以各改各的。
调整破风系数不会影响转会市场，调整薪资曲线不会影响爬坡速度。

### sim —— 比赛引擎

没有胜负判定。每秒循环四步：聚集团 → 定集团速度 → 每人反解跟住要多少瓦 →
扣能量账。名次是这个循环的副产品，掉队、追回、爆掉、终点绝杀全部涌现，
没有一行脚本。详见 [`source/sim/README.md`](source/sim/README.md)。

标定结果（对照公开的职业赛数据）：

| 项目 | 引擎输出 | 现实参考 |
|---|---|---|
| 13.8km @ 8.1% 单人爬坡 | 40.3 分 / 1664 m/h | 37–45 分 / 1350–1750 m/h |
| 180km 平路赛段均速 | 41.1 km/h | 40–45 |
| 165km / 4378m 山地赛段均速 | 30.5 km/h | 29–34 |
| 38km 个人计时赛均速 | 45.3 km/h | 44–53 |
| 199km 石板路赛段均速 | 40.6 km/h | 38–45 |
| 突围最大领先 | 4.7–5.7 分 | 3–8 分 |

行为层面：山地赛段前八全是总成绩核心和爬坡手、亚军差 6.8 秒（一个五人的
山顶终点小组）、完赛率 87%；平路赛段前八清一色冲刺手、亚军差 0.06 秒、
完赛率 100%——一场教科书式的集团冲刺；石板路前八全是突围型车手。

**追击控制器的人力项在 45 人处封顶，这一条曾经悄悄决定了平路赛段的胜负。**
112 人的场地上集团冲刺，160 人的场地上十个人的突围能守住 26 秒——集团越大
突围越强，这个规模阈值纯粹是模型产物。原因是不对称：集团变大只喂强了突围
（更多人有本钱攻出去），却没有喂强追击（人力封顶了）。现实里一百六十人的
主集团有七八支队各带一个冲刺手，愿意上前干活的人是四十五人集团的三四倍，
而突围那边人多只是轮转更省力，收益远没有这么大。把封顶放宽到 120 人之后，
平路赛段变成了完赛率 100%、前八全是冲刺手、亚军差 0.06 秒的集团冲刺，
四条标定赛道也全部仍然通过。

**集团速度模型**是这一层的核心。集团的速度不由最前面那个人决定，而由
**全员的平均每人成本**决定：强度 × 平均 CP 的功率，摊在"平均迎风面积 ×
平均破风系数"上。这一个系数同时解释了四件事——为什么平路大集团谁都跟得住、
为什么爬坡时集团必然碎掉、为什么突围人越多越能活、以及为什么终点前
主集团一提速就能吞掉所有人。

强度曲线是按"顶风者成本"标定的，引擎会自己算出到"全员平均成本"的换算比
（平路约 0.63，陡坡接近 1.0）。手填一个固定折算系数行不通——试过，
平路刚好，山地赛段直接慢掉七公里每小时。

### game —— 世界与赛季

**双轨结算**是这一层最重要的设计。完整引擎跑一场比赛要十几秒，一个赛季
107 个比赛日就是 25 分钟，玩家不可能接受。所以：

- 玩家要亲自看的比赛 → 完整引擎逐秒模拟
- 其余比赛 → 快速结算，整季 0.1 秒跑完

两者不是两套规则。快速结算把引擎的物理结论压成闭式公式，
`calibrate_quick.py` 逐条对账：冠军成绩偏差 < 0.5%，差距分布、前十角色
构成都在容差内。玩家不会察觉自己看的比赛和系统替他跑的比赛遵循不同规律。

**世界数据**（`data/world.json`，160 名车手 / 20 支车队 / 24 个赞助商 /
25 场赛事）里每个实体都带 `art_*` 字段，直接指向 `assets/art` 下的文件名。
GPT 出的图一落盘就能挂上，前端拿到 JSON 就知道加载哪张。

**经营循环**：赛季成绩 → 赞助商满意度 → 下赛季预算 → 能签什么人 →
阵容实力 → 赛季成绩。每一环都有可以说清楚的因果，没有纯随机。

### tools —— 生产管线

`asset_audit.py` 回答三个问题：还缺什么、合不合规、
world.json 里的美术引用能不能全部命中硬盘上的文件。

当前状态：**253 / 253 张（100%）**，数据引用对账 93/93 全部命中，
20 张事件插画全在。硬盘上实际有 369 个 PNG（有富余）。

出图那边交回来的命名和游戏数据里的逻辑名对不上（`sponsor-07.png` vs
`sponsor-logo-07`、`event-12-media-scrutiny.png` vs `event-12`）。三种解法
只有一种是对的：改数据要跟着每批出图改一遍、改文件名是让美术白干还治标不治本，
所以加了一层解析（`game/assets.py`）——**给人看的名字和给程序看的名字本来就该分开**，
出图可以在文件名里带描述，游戏只认前缀里的序号。

## 可视化原型

`原型_比赛回放.html`（双击打开，不需要起服务器）用真实美术资源播放一场
完整引擎跑出来的山地赛段，专门验证美术清单第五节点名的两件事：

## 玩家指令层

`game/orders.py` 把玩家的意志接进物理引擎。八条单人指令（护航队长、抢突围、
冲刺争胜、山地进攻、保存体力……）和五套整队预设（总成绩优先、冲刺夺段、
全员抢突围、山地强攻、保存实力）。

设计上有一条硬规矩：**指令不直接改成绩，只改行为**。一条"山地进攻"做的是
提高攻击触发概率、让车手更舍得烧无氧储备，而不是给他加百分之几的速度。
攻击成不成功仍然由物理和能量决定。一旦允许指令直接加成绩，玩家会立刻发现
最优解是"永远选最激进的那个"，战术层就退化成一个装饰性的下拉菜单。

引擎侧只认识六个中立的行为乘数（`sim.tactics.Directive`），完全不知道
"指令"这个概念。战术玩法怎么改都不会动到物理层。

```bash
python3 source/verify_orders.py --stage flat --runs 3 --team T05
```

验证结果（平路赛段，中游队伍 T05，两个随机种子）：不下指令时最好名次 13.0，
「冲刺夺段」14.5，「全员抢突围」22.0——**打法之间有 9 位的名次跨度**。
把八个人全撒出去抢突围会把队伍拖垮，这个结果本身就是有意义的反馈。

## 事件系统

`game/events.py`，20 个事件、54 个选项、9 个带风险判定。三条规矩：

**每个选项都要有代价。** 全部是「拿 A 换 B」，没有免费的好处——如果有一个
选项永远是对的，玩家点三次就看穿了，之后所有事件都变成无脑点确认。

**后果要能被追溯。** 士气、疲劳、属性、资金、声望全部真实写进世界数据，
玩家能在阵容表里看见。弹一个窗然后什么都不改，是这类系统最糟糕的做法。

**不确定性放在结果上，不放在是否发生上。** 玩家做完选择才掷骰子。
前者是赌博，后者是欺骗。

`python3 source/tools/export_art_briefs.py` 会把 20 张事件插画的出图简报
导出成 `事件插画_出图简报.md`——含统一风格锁、每张的画面描述与情绪定位，
复制给 GPT 就能开工。

## 交互式经理原型

`原型_车队经理.html`（双击打开）。三个页签：

**阵容** —— 八名车手的总评、潜力、年薪、合同、士气，以及头号车手的九项属性条。

**赛前部署** —— 六场不同地形的比赛 × 五种打法，全部预先算好。换个打法，
结果是真的不一样：

| 赛段 | 最优打法 | 最差打法 | 名次差 |
|---|---|---|---|
| 阿登丘陵赛（山顶终点） | 山地强攻 第 5 | 保存实力 第 18 | 13 位 |
| 石板路经典赛 | 保存实力 第 5 | 全员抢突围 第 19 | 14 位 |
| 春季山地赛 | 山地强攻 第 24 | 全员抢突围 第 33 | 9 位 |

**关键在于没有一种打法在所有赛段上都最优**——山地赛段上「冲刺夺段」会白白
消耗掉冲刺手，平路赛段上「山地强攻」等于什么都没做。这正是战术层应该有的样子。

**俱乐部事务** —— 真的做选择，立刻看到后果落在哪些数字上。

## 摔车与机械故障

`sim/incidents.py`。这是引擎里唯一的「意外」来源，也是最容易做砸的一块——
做砸的方式只有一种：把它做成纯随机。玩家输掉一场比赛，如果原因是一个
和他所有决定都无关的骰子，他不会觉得可惜，只会觉得被耍了。

所以每一份风险都挂在**玩家能看见、也能影响的东西**上：

| 因素 | 效果 | 玩家怎么应对 |
|---|---|---|
| 路面（石板/砾石） | 摔车 ×6.5，机械 ×15 | 赛前就能在赛道数据里看到 |
| 雨天 | 风险 ×3.0 | 影响押不押安全的轮胎 |
| 弯道密度 × 下坡速度 | 下坡时 ×1–4.2 | 「下坡」属性同时是收益和风险 |
| 在集团里的纵深 | 埋得越深 ×3.1 | **省力和安全是矛盾的** |
| 无氧储备见底 | ×1.9 | 「保存体力」有了第二层意义 |

集团位置那一条是全套里最漂亮的权衡：躲在集团中间最省力，但也最容易被
前面的连环摔波及。

后果以损失时间为主（中位数 26 秒，爆胎换轮最常见），退赛占全部意外的
0–8%。在主集团里出故障队车马上就到，跑在突围里或已经掉队的人要等中立
器材车，时间翻倍——这让「待在集团里」多了一个理由。

天气由赛季层按地形抽取（比利时的春天 42% 下雨，西班牙的沙漠 4%），
完整引擎和快速结算共用同一份天气，两边的意外率也标定到同一个量级。

```bash
python3 source/verify_incidents.py     # 11 项验证，全部通过
```

## 升降级

`management.apply_promotion_relegation()`。三个等级之间每个赛季各交换一支队，
依据是**三年滚动积分**。

单赛季定生死是最容易想到、也最糟糕的做法：一支队可能因为核心车手在五月
摔断锁骨就掉一级，而玩家对此无能为力。用三年滚动之后，一个坏赛季会让你
进入降级区、但还有两年时间补救——这才让「长期规划」有意义，也才有真正的
降级保卫战可打。现实中的 UCI 用的正是三年滚动。

降级不只是换个标签，四件事同时发生：基础拨款掉一档、赞助商重谈（预算 ×0.80）、
声望 −8、**总评 76 以上的车手有 55% 概率触发解约条款走人**。最后一条最痛——
现实中顶级车手的合同几乎都写着「球队失去世巡赛资格即可自由离队」。

还有一条保险：如果升级候选的滚动积分并不高于要降级的那支队，这一年就不换。
免得出现「升上去的比降下来的还弱」这种荒唐结果。

`relegation_table()` 提供随时可查的形势表——玩家每年最该盯的就是这张。

六个赛季的推演里升降级每年都在发生，但没有一支队被一次意外打死：

```
2026  ↑ 云杉家居 洲际队 → 职业队      ↓ 风隼装备 职业队 → 洲际队
2027  ↑ 驰远轮胎 洲际队 → 职业队      ↓ 磐石建材 职业队 → 洲际队
2028  ↑ 云杉家居 职业队 → 世巡赛      ↓ 擎云科技 世巡赛 → 职业队
```

## 生涯：把所有系统串成一条时间线

`game/career.py`。在这之前每个系统都能单独跑，但没有任何东西把它们连起来
——没有存档，没有「下一步该干什么」，关掉终端一切归零。

三个设计决定：**一切通过 `advance()` 一个 API 推进**（CLI、HTML、以后的
Unity 调同一个函数，不会出现两套逻辑对不上）；**决策是排队的不是弹窗打断的**
（赛前指令、事件、转会、训练进同一个队列，可以攒着一起处理，也可以按默认值
一键跑完）；**存档是纯数据**（整个生涯一个 JSON，能跨版本读、能手改、能分享）。

### 转会与合同

`game/market.py`。**玩家和 AI 走同一套评估函数**——车手怎么看一份报价只有
`evaluate_offer` 一个实现。给 AI 另写一套简化逻辑，玩家迟早会找到一个
「AI 看不懂但车手会接受」的套利姿势，整个市场就崩了。

车手看四件事：钱（给到市场价 1.3 倍以上收益递减）、出场机会（80 分的爬坡手
不会去已经有两个 85 分爬坡手的队）、队伍档次、年龄（30 岁以上更看重钱，
年轻人更看重位置）。

界面上标的价格是「按他的标准，我们这支队签下他大概需要多少」，已经把档次和
出场机会折算进去了。只报经纪人开价的话，玩家每次都被截胡而且不知道差在哪
——那不是难度，是信息不透明。

### 训练

`game/training.py`。六套专项方案、三档强度、四种集训营。**训练必须是取舍**：
专项让重点属性涨得快、其余几乎不涨；大强度涨得更快但赛季初带疲劳、受伤风险
翻倍；集训营花钱买成长但占掉恢复时间。

实测一名 22 岁工兵在大强度爬坡专项下四个赛季：总评 58 → 68，爬坡 55 → 63，
冲刺只从 49 涨到 51。专项化是看得见的，而且要等三四个赛季——这个等待本身
就是经理游戏最好的钩子。

## 赛道：数据驱动与可视化编辑

在这之前 25 条赛道全是程序生成的——策划改不动、玩家改不动，也没法把真实
赛事搬进来。现在赛道是 `data/courses/*.json`（107 个赛段），程序生成从
「唯一来源」降级成「给你一份初稿」。

```bash
python3 source/tools/export_courses.py    # 导出初稿（不覆盖改过的）
python3 source/course_check.py E13-5      # 一条赛道的体检报告
python3 source/course_check.py --all      # 全部赛道校验
python3 source/tools/build_editor.py      # 生成可视化编辑器
```

**文件存在就以文件为准**，`load_course()` 找不到才回退到生成。改过的赛道
不会在下次导出时被悄悄覆盖。格式刻意用公里和百分数而不是引擎内部的米和
tan 值——打开文件应该能直接看懂「12.4 公里、8.2%」。

**校验挡在引擎前面。** 手编数据里的 40% 坡度、负数长度、越界的爬坡点，
会让引擎算出荒唐结果或直接崩。问题分「错误」和「警告」两级：错误挡住不放行，
警告只提示（有些极端赛道是作者故意的）。

### 体检报告

设计赛道最难受的是改完不知道自己改了什么——跑一场完整模拟要二十几秒，
迭代不起来。`course_report` 用快速结算的物理结论，几毫秒给出判断：

```
盛夏大环赛 第 5 赛段　125.1 km　爬升 3053 m
  预计冠军均速  31.1 km/h    用时约 4 小时 1 分     ↳ 想改：改总长度或累计爬升
  每公里爬升   24.4 m/km    高山。大环赛决胜赛段就在这个区间
  选拔性      强           集团会被撕开，只有状态好的人能留在前面
  决胜点      6 处          终点陡段（剩 0km，9.8%）、HC 爬坡（剩 88km，10.7%）
  利好程度：总成绩核心 89%　爬坡手 84%　平路手 59%　突围手 57%
  · 山顶终点：差距会一直拉到最后一米。
  · 开场就有陡坡：突围很难形成，因为前 15 分钟本来就是全场最快的时候。
```

**每一项都附「想改的话动什么」**——一份只报「难度 7.2 分」的报告没有用，
作者不知道该动哪儿。

### 可视化编辑器

`赛道编辑器.html`（双击打开）。107 条赛道随便切换，剖面按坡度上色（红 >8%、
橙 4-8%、蓝下坡、米色石板路），改任何一个数字，右侧的体检、利好分析、
提醒和校验实时更新。改完导出 JSON 覆盖回 `data/courses/` 即可生效。

编辑器里的判断逻辑是 `course_report` 的 JS 镜像，公式逐字对齐——实测三条
赛道的预测均速两边完全一致（30.6 / 38.9 / 38.0 km/h）。作者看到的预测必须
和引擎真跑的结果对得上，否则这个工具就是在误导人。

## 真实地理

`data/climbs.json` + `game/climbs.py`。17 座真实山口、8 段真实石板路，
按公开路书与等高线录入。

**法务边界写在代码最前面**：真实赛事名称（环法、巴黎-鲁贝）是注册商标，
真实车手姓名涉及人格权，游戏里一律用虚构的；但山口名称和海拔剖面属于
公开地理事实。所以录的是**山**，拼出来的**赛事名是虚构的**。

**关键在于每座山都拆成了分段，而不是只记平均坡度。** 阿尔普迪埃兹平均
8.2%，但起手第一公里是 10.6%，集团正是在那里第一次被撕开；旺图山前 6 公里
几乎是平的，真正的战斗在圣埃斯泰弗弯之后。只记平均值的话，引擎里所有的山
会变成同一座山——爬得快的人赢，没有别的故事。

这也是真实地理相对程序生成的全部价值：**不规则性**。程序生成的山坡度平滑、
节奏均匀；真实的山有喘息处、有假顶、有最后一公里突然立起来。

```bash
python3 source/tools/build_real_courses.py   # 拼装七条对标经典赛的赛段
```

| 赛道 | 构成 | 引擎跑出来 |
|---|---|---|
| 高山之王 | 加利比耶 + 马德莱娜 + 阿尔普迪埃兹山顶终点 | 141 km / 爬升 3971 m |
| 双子山口 | 莫尔蒂罗洛 + 斯泰尔维奥 | 冠军是总成绩核心，亚军 +3.9s |
| 终极陡坡 | 安格利鲁山顶终点 | 前八 3 个总成绩核心 + 3 个爬坡手 |
| 阿登之墙 | 拉勒杜特 ×2 + 于伊之墙终点 | 冠军是总成绩核心，亚军 +3.2s |
| 北方地狱 | 阿伦贝格、树之路口等 8 段石板 | 石板 15.9 km，冠军是冲刺手 |
| 佛兰德之环 | 老克瓦雷蒙 ×2 + 科彭堡 + 帕特堡 | 短陡石板坡密集排在最后 40 km |
| 利古里亚海岸 | 奇普雷萨 + 波焦，终点前 5 km 下坡 | 259 km，集团冲刺 |

### 真实地理反过来修好了两个东西

**体检报告的「利好谁」原本是错的。** 阿登之墙全程只有 4.8 m/km，按全程
平均算被判成「平坦、利好冲刺手 87%」——而它的终点是 19% 的于伊之墙，
真实结果是冲刺手一个都活不下来。加了「决胜段难度」之后（多个窗口按离终点
的远近加权取最大），同一条赛道读数变成总成绩核心 92%、爬坡手 90%。
**决定胜负的不是总爬升，而是爬升在哪儿。**

**突围在山地赛段的强度是错的。** 突围的全部优势来自「几个人轮流破风、
把每人成本摊到七成以下」，但陡坡上根本没有风可以破——功率几乎全部对抗
重力，五个人轮转省不下任何东西。修正之后，双子山口和终极陡坡都回到了
总成绩核心夺冠、亚军差几秒的正确形态。

## 赛历数据化

赛道数据化之后，最后一块写死的东西是赛历——25 场赛事排在哪天、每场几个赛段、
什么地形，全在一张常量表里。玩家想自己造一个大环赛，或者把七条真实赛道编成
一个古典赛赛季，做不到。

```bash
python3 source/calendar_check.py --export        # 导出成可编辑 JSON
python3 source/calendar_check.py                 # 赛季节奏体检
python3 source/tools/build_calendar_editor.py    # 生成赛历编辑器
```

赛段构成用字母串描述：`FHIFMSF` = 平路-丘陵-计时-平路-山地-山顶-平路。
一个 21 赛段的大环赛写成数组要 21 行，写成一行字母，整场比赛的节奏一眼就
能看出来。改一个字母，`generate_world.py` 立刻读到新构成。

**赛历体检比单条赛道的体检更重要。** 单条赛道跑歪了只毁一场比赛；赛历排歪了
会毁掉整个赛季——比如全年 80% 是平路赛段，爬坡手一整年无事可做，玩家阵容里
就永远不该有爬坡手。这类问题在单场比赛里完全看不出来。

体检查四件事：**地形配比**（每类车手全年有没有足够的比赛日，不够就直说这个
角色会闲置）、**顶级赛事间隔**（少于 14 天，同一批核心无法两场都打）、
**日期冲突**（两场顶级赛事重叠会把车队撕成两半，中小赛事撞车则是常态）、
**赛季分布**（前后半季场次差太多，玩家会觉得赛季在空转）。

`赛历编辑器.html` 用甘特图画整个赛季，按赛事等级上色，改任何一格右侧的
体检和校验实时更新。判断逻辑同样是 Python 侧的 JS 镜像，实测两边读数一致
（25 场 / 107 个比赛日 / 顶级赛事最小间隔 7 天）。

## 成绩数据库与历史

在这之前，一个赛季跑完除了积分和几条动态之外什么都不剩。`game/records.py`
用标准库的 SQLite 把每一场比赛的前 12 名存下来，三张表：`results`（每个
赛段的名次、用时、差距）、`seasons`（车队年度排名与预算）、`rider_seasons`
（每名车手每一年的年龄、总评、胜场、比赛日）。不引入任何依赖。

接入方式是一个回调，不是一个 import：`run_event(..., recorder=fn)`。
**比赛引擎不该知道「数据库」这种东西存在**——它把成绩交出去，要不要落库、
落到哪儿，由生涯层决定。不挂数据库照样能玩，只是没有历史。

```bash
python3 source/history.py --sim 25              # 空跑 25 季再出报告
python3 source/history.py --balance             # 只看平衡诊断
python3 source/tools/export_history.py --db data/records.db   # 出 HTML
```

`历史档案.html` 是单文件、数据内联、双击就开。上半页是玩家看的名人堂、
赛道纪录、车队王朝；下半页是设计者看的平衡诊断。放在一起是故意的：
**判断「这个世界可不可信」和判断「这套数值平不平衡」用的是同一批数字。**

### 它立刻抓出了三个平衡 bug

这套东西的价值不在于「能查历史」，而在于**平衡问题在单个赛季里根本看不见**。
25 个赛季一堆起来，三条结论直接跳出来：

**一、集团冲刺是完全确定的。** 快速结算里终点名次按冲刺速度排序，
一点随机都没有——于是全世界最快的那个人赢下他参加的每一场平路赛段。
25 季跑完，一名车手拿了 233 场冠军，其中 177 场是大环赛赛段。
现实里最好的冲刺手一年赢十几场，不是每场都赢：抢位、被关、列车散架、
前面有人摔，这些才是冲刺的常态。加了 `SPRINT_CHAOS`（σ=0.052）和
抢位系数之后，历史第一从 233 场降到 138 场。
附带修好了另一件事：`positioning` 这条属性原本只在完整引擎里有用，
快速结算完全无视它——同一条属性在两套结算里意义不同，是设计上的裂缝。

**二、丘陵和石板路变成了平路。** 原来终点冲刺只按「跟住了没有」二分，
跟住的人一律平等。于是丘陵赛段 66%、石板路赛段 76% 被纯冲刺手拿走。
翻过四千米爬升之后，那个刚好没掉队的人不可能再赢冲刺——加了
`FATIGUE_AT_LINE`（平路 0.25，丘陵 1.70，石板 2.10）之后：
石板路变成全能型 60% + 突围手 14%，丘陵变成全能型 33%，冲刺手降到 21%。
这个改动同时让快速结算和完整引擎在石板路上的前十角色重叠从 50% 升到 80%。

**三、突围手这个角色不存在。** 原来给的是 `1 + random×0.012`，万分之几，
等于没给：突围手 per100 只有 4.8，是所有角色里最低的一半。
突围本来就该是「多数时候被抓回，偶尔成功一整天」的形状，那是一次抽奖，
不是一点点平均加成。改成按地形的中奖概率（山地 16%、石板 40%）之后
升到 20.6，和完整引擎跑出来的「石板路前十有五个突围手」对上了。

改完之后四条标定赛道全部仍然通过（平路 1.3% / 山地 0.7% /
计时 0.2% / 石板 1.5% 偏差）——**平衡改动没有以牺牲物理为代价。**

### 最有用的两张表

`role_balance` 的关键列是 `per100`（每一百个「车手赛季」赢几场），不是
`wins`。原始胜场数必然是工兵最多，他们占了半个车队。**只有除以人数，
才知道「当一名爬坡手」和「当一名工兵」哪个更有价值**——看原始数字会
得出完全相反的结论。

`wins_by_stage_type` 是地形 × 角色的矩阵，也是最硬的一张表：如果山地赛段
的冠军里冲刺手占两成，说明地形根本没在筛人，前面那几百条赛道白设计了。
当前读数：平路 冲刺手 67%，山顶终点 爬坡手 54%，石板路 全能型 60%，
计时赛 全能型 41%——每种地形都有明确的主人。

## 参赛名单：修一个藏了很久的 bug 才让它有意义

战术板上多了一列勾选框：这场派谁、谁留着养疲劳，名额按赛事等级从 6 到 8。
还有一个「挑最不累的」按钮。

但做到一半发现这个功能是空的——**疲劳恢复在生涯模式里从来没被调用过。**
`season.py` 里那段「两场赛事之间的空档所有人回血」只写在批量赛季那条路径上，
`career.py` 从来没调。后果是跑到第 12 场比赛，全世界所有人的疲劳一起顶到
1.0，然后一直顶到赛季结束。

**因为是所有人一起顶满，相对强弱没变，成绩表看上去完全正常——所以它藏了
很久。** 但它悄悄抹掉了一整个玩法维度：轮换阵容、让人休息、恢复属性值不值钱，
在一个疲劳封顶的世界里全都没有意义。

把恢复抽成 `season.rest()` 让两条路径共用，同时把每个比赛日的疲劳从 0.075
压到 0.042——0.075 时一个 21 天的大环赛要加 1.8，顶到上限还溢出一倍，
跑完的人和跑崩的人都是 1.0，疲劳这条轴在大环赛之后没有分辨率。修完之后
一个赛季里队内疲劳的最大差距是 0.61，恢复属性和轮换终于开始值钱。

`verify_play.py` 里加了两条盯着它：「疲劳真的会累积」和
「**队内疲劳有差异**（轮换才有意义）」。第二条就是这个 bug 的守门人。

## 团体计时赛

引擎里最后一个补上物理表达的赛段类型（`sim/ttt.py`）。它值得单独建模的
理由只有一条：**一支队不是「跑得多快」，是「能带着几个人跑多快」。**
成绩取第 N 个人过线的时间，所以把队尾榨干甩掉能提速，但甩掉计时位那个人
就等于自杀。

没有复用主赛程那台引擎：`race.py` 的核心是「集团怎么形成、谁跟得住谁」，
而团体计时赛里没有集团博弈、没有战术、队伍之间也不互相影响。硬套要关掉
一半机制，不如照它真正的物理写一份短的：**轮转、掉队、取第 N 人。**
物理本身仍用同一套 `physics` 和 `energy`，瓦特和别处是一回事。

两个数字是试出来的，都不是一开始想对的：

**配速由「必须活到终点的那个最弱的人」决定，不是全队平均。** 第一版按
全队平均 CP 配速，结果每支队都恰好剩下 4 个人——配速定义成「平均那个人
刚好到极限」，弱于平均的一半必然被榨干。那不是模拟，是同义反复，而且
二十支队长得一模一样。

**强者拉长班，弱者拉短班。** 平均轮转（每人 1/N 时间）会让任何弱于配速者
的人必然掉队，同样导致所有队都剩 need 个人。真实的团体计时赛领骑时间是
按能力分配的：强的人拉一分钟，弱的人上去露个头就下来。加上之后，完赛人数
才从「清一色 4 人」变成 4–7 人不等。

验证里出了一个**我预期反了、而它是对的**的结果：取第 6 人计时比取第 4 人
更快。我以为「要带更多人到线」必然更慢，但配速由计时位那人决定，取第 6 人
时配速更保守，八个人全留下来分摊领骑，每人在风里的时间少了一半，可持续的
速度反而更高。**一支整整齐齐的队，比一支炸掉之后只剩四个人硬顶的队更快**
——这正是现实里教练拼命不让人掉队的原因，也是这个模型没白写的证据：
它给出了一个我没有事先写进去的结论。

**已经排进赛历**：三个大环赛的开幕赛段都是团体计时赛（`T` 字母），
这也是现实中的常见安排——短、快、把全队摆上台面，第一天就能拉开
一两分钟，为整个三周定调。实跑一场 37 km 的开幕赛段：最快的队 55.1 km/h，
第一名到最后一名差 226 秒。

赛历字母表、赛段积分表、奖励秒数规则也一并补齐了。团体计时赛不发
分数榜积分（赢的是一整支队，把 50 分发给「排最前面那个」纯属抽签），
也没有奖励秒数——现实里两条规则都是这样。

当前读数：28 km 赛道均速 51.0–54.8 km/h（现实 50–58），队伍之间拉开
一到三分钟，同样的前四人换上更强的队尾快 86 秒——**全游戏唯一一个
「第五到第八人有多强」直接决定成绩的地方。**

顺带修了一个相关的坑：`build_course` 一直是「有数据文件就以文件为准」，
但赛历把某个赛段改成团体计时赛之后，硬盘上还存着它原来那条 200 公里的
公路赛道，团体计时赛的模型拿着它跑三小时也跑不完。
**「以文件为准」的前提是文件说的还是同一件事**——现在会比对赛段类型。

## 亲自看一场比赛

赛前页上除了「出发」还有一个「亲自看这一场」。点下去，那台逐秒物理引擎
会真的把这个赛段跑一遍，然后把过程播给你看：突围什么时候形成、领先多少、
主集团什么时候开始收网、你的队长还剩多少无氧储备、谁在最后一个坡上掉了。

**在这之前那台引擎一次也没被玩家看见过。** 它是整个项目最强的一块——
所有这些都是从物理里涌现的，没有一行脚本——而玩家点「出发」，一秒后
看到一张成绩表。

三个设计决定：

**录集团和差距，不录一百六十个人的坐标。** 电视转播也不这么给——镜头给的
是「突围三人，领先两分四十；主集团在后面，我方队长在集团里」。这既是正确的
抽象，也让回放数据小两个数量级（180 KB 而不是十几兆）。

**播报要铺满整场。** 引擎一场比赛产出好几百条事件，而且不是均匀分布的，
终点前二十公里最密集。第一版取最后 160 条，结果回放的前四个小时播报栏
一片空白——**而那恰恰是突围形成、集团放走的那一段**。改成按时间均匀抽稀
之后，动态跨度从「最后 40 分钟」变成整场 253 分钟。

**看到的必须算数。** 录制返回的名次和用时直接进入总成绩。如果看完之后
系统再用快速结算重跑一遍，那他刚才看的四十分钟就是一场表演——完整引擎
在这里不是特效，是判决。

### 画面

用的是美术清单里那套五层卷轴和三头身车手，一直摆在 `原型_比赛回放.html`
里没接进游戏。现在接上了：远山、中景、路边、路面、前景五层按各自的视差
速度卷动，车手按集团一簇一簇地画，每支队染自己的队服色——
**队服不出图，一张灰度姿势图程序染色**，二十支队不占任何额外美术工作量。

横轴不是里程，是**时间差**。领先两分钟的突围按里程算在画面外八百米处，
永远看不见；按时间差压缩之后，转播里那句「领先两分十秒」直接就是画面上
的距离。

还有一条是试出来的：**主集团必须永远在画面上**。第一版取最前面五个集团，
结果比赛中段前面全是零散的突围和掉队者，一百多人的主集团反而不见了——
观众最想知道的「后面追得怎么样」看不到。改成「前四个集团 + 主集团」。

代价是时间：一个赛段二三十秒。所以它是玩家主动选的，其余比赛仍然走
快速结算。`verify_play.py` 里加了十三项检查盯着这条路，包括「动态铺满整场
而不是挤在终点前」和「主集团永远在画面上」这两条。

## 战术：从「界面上的一个下拉框」变成真的战术

可玩版本做完之后，第一件该查的事是玩家的选择到底有没有用。查下来发现
**打法完全没有生效**：`career` 每场比赛都老老实实算了一份 orders，
然后原样扔掉——`run_event` 根本没有这个参数，快速结算也不知道「指令」
这回事。完整引擎认得 Directive（`verify_orders.py` 一直在证明这一点），
但赛季里跑的是快速结算。**玩家唯一的战术杠杆，在整个生涯模式里是空的。**

补这条线要回答一个问题：战术在一个闭式解里到底意味着什么。四条，
每条对应一个物理现实：

领骑要顶风，`pull_bias` 越高自己越累、赢的机会越小；有人顶风就有人省力，
队友顶的风加起来喂给被保护的那个人；`spend_bias` 与 `conserve` 直接改
今天的输出，换的是后面赛段的体力；`sprint_bias` 只动终点那两百米，
不动全程能力。系数都很小，因为能力差 1% 就是慢 1%——五小时的比赛里
那是三分钟。

代价是相对「正常轮换领骑」算的，不是相对零。这一点很容易搞错：如果按
绝对值扣，「自由发挥」会凭空变成一个负面选项，而它本该是中性的那一个。

掩护收益按车队结算，保护两个人就每人分一半。**这就是经理游戏的核心取舍：
围绕一个人建队，还是两头下注。**

`verify_tactics.py` 是这条线的看门人：先把八条指令的数值含义摊开
（护航队长 −0.44% 能力 / −3.8% 冲刺，山地进攻 +1.05% 能力但波动翻倍），
再用同一个种子、同一支队跑五种打法各一个赛季。当前读数是夺冠 0–2 次、
前十 6–11 次、积分 758–2316——**没有哪套打法普遍最优，取决于你手里
是什么人**，这正是要的效果。界面上的战术板可以逐人下令覆盖打法，
车手按「这条赛道有多适合他」排序。

### 补完这条线，顺手修好了四个平衡问题

指令一旦生效，很多原来说不通的数字自己就对了。25 个赛季的诊断：

工兵的 per100 从 27.6 掉到 13.3。他们本来就该在前面顶风然后自己什么都
拿不到，之前不掉是因为「护航」这两个字没有任何数值含义。

全能型的默认指令原来是「全程干活」。那个默认在完整引擎里跑单场没问题，
但把它当成全世界所有全能型每一天的默认，等于宣布这个角色永远不赢——
per100 从 113 掉到 38，丘陵赛段的冠军全被冲刺手接手。**默认值不是
「典型行为」，是「没人管他的时候他为自己做什么」。** 改成自由发挥后回到 84。

计时赛里不该有战术。没有集团、没有风可挡、没有列车可带，领骑掩护冲刺
三件事全都不存在——不做这个区分，一支工兵成群的队会在计时赛里凭空
得到掩护收益。

**同一个集团判同一时间。** 之前快速结算给的是「冠军成绩 + 名次 × 0.06 秒」，
本意是「名次差不影响总成绩」，但它影响了：21 个赛段累积一秒多，而短分站赛
的总成绩前二本来就只差几秒。跑 25 个赛季，冲刺手拿走 30% 的总成绩冠军，
亚军平均只落后 6.6 秒，最小 0.0 秒——**那不是比赛结果，是浮点数排序的
副产品。** 改成同时间之后，短分站赛由谁收集奖励秒数决定；10/6/4 秒是
UCI 的真实规则，`classification.py` 里一直写着，只是从来没起过作用，
因为每个人的时间本来就不一样。

### 两个角色画像也一并重做了

**总成绩核心原来赢不了任何东西。** 爬坡 +18 比纯爬坡手低 8，体重还多
四公斤，每公斤功率打不过爬坡手；计时 +16 又打不过全能型的专精。他的
per100 是全部角色里最低的，却是队里最贵的那个人——设计上的自相矛盾。
现实里的大环赛冠军不是全能型，是「会计时赛的顶级爬坡手」，所以爬坡拉到
+24、体重压到 58–66、再加恢复和韧性。

**纯爬坡手要为「纯」付出代价。** 原来他爬得最好，耐力和恢复还都是正的，
那他就是一个更便宜更强的总成绩核心。现实里纯爬坡手赢的是山地赛段而不是
三周大环赛——他在第二周会掉下去。把耐力和恢复压到负值，游戏里那套逐日
累积的疲劳就会替我们表达这件事，不需要额外写一条「爬坡手第 14 天开始
变弱」的规则。

四条标定赛道改完全部仍然通过（平路 1.7% / 山地 0.5% / 计时 0.2% /
石板 0.5% 偏差），石板路还因为补了「体重在颠簸里是优势」而从 40% 升到 60%
角色重叠。

## 已知问题

**平路的集团凝聚力：查清楚了，也知道怎么修，但修不动——因为它和突围控制
是同一条曲线上的两件事。** 世巡赛级别的集团里，一分钟内完赛的比例是 42%，
现实是 85–95%。

这一路排除了四个嫌疑。重新拟合 `GAP_SHAPE["flat"]`：中位数对上了，
但冲刺手全被甩掉、角色重叠从 60% 掉到 30%——`_flat_merit` 把冲刺手排在
后面**是正确的物理**，他们赢比赛靠的是终点那两百米。加强破风：大集团破风
0.575 → 0.42，一分钟内完赛的人从 11 个变成 12 个，因为集团速度定义成
「平均每人成本等于标定强度」，所有人省力集团只会骑更快。测试集团混进洲际队：
收到 `spread=0.18` 只留世巡赛级别，比例从 7% 升到 42%——**这一条是真的，
但只解释了一半。** 追击控制器的人力项在 45 人处封顶：修完之后领奖台完全
正常了（完赛率 100%、前八清一色冲刺手、亚军差 0.06 秒）。

最后一条嫌疑是这次才找到的。测「谁在赛段的什么位置掉队」，结果掉队**全部
堆在 78% 和 94% 两个点上**——那正是 `base_intensity` 两级台阶所在的位置。
强度从 0.96 一步跳到 1.03、再跳到 1.12，一整批车手在跳变的那一秒同时被
推过极限，没有适应的余地。真实比赛的节奏是拧上去的，不是跳上去的。

改成在同样的控制点之间线性插值（端点值不变，所以均速不受影响）：
**一分钟内完赛从 42% 升到 68%，中位差距从 64 秒降到 23 秒。** 机制是对的。

但同一次改动让平路赛段的前八变成清一色突围手：节奏拧上去的时候不再有
那一下猛的，收网期的追击就软了。**凝聚力和突围控制在这条曲线上是耦合的**,
动它必须连 `chase_boost` 一起重调，那是一次完整的重新标定，不是一个补丁。
所以退回了阶梯版——用一个已知的缺陷，换掉一个更糟的缺陷。整个过程和
可复现的数字都记在 `sim/tactics.py` 的注释里。

**总成绩核心当上大环赛冠军了，但真正的原因不是我一开始以为的那个。**
按人均算，大环赛总成绩从「爬坡手 5.38 / 总成绩核心 1.23」变成
「总成绩核心 12.31 / 爬坡手 4.00」。为此我调了属性画像、赛季目标、
阵容配方三轮，**全都没打中**。

线索是一句被忽略的话：2026 赛季三个大环赛冠军全是总成绩核心，
2027 年之后全是爬坡手。**世界不是慢慢漂的，是一夜之间被重新贴了标签。**
初始世界照配方生成，所以第一年对；跑完一次休赛期的角色重排就变了。

`reassign_roles` 用全局贪心：算出每个人对每个角色的契合度，从最高的开始
占坑。问题在不同角色画像的「峰度」不一样——爬坡手是 0.60×爬坡，权重集中；
总成绩核心是 0.35×爬坡+0.30×计时+0.20×耐力+0.15×韧性，摊得很平。
**一个顶级爬坡型车手在「爬坡手」上的原始分永远高于他在「总成绩核心」上的
原始分**，于是每支队最好的那个人被贴上爬坡手，队长的位置留给第二好的。
这个世界从第二年起就不再有真正的队长了。

第一版修法是「按角色重要性依次填坑」，队长先选人。矫枉过正：每支队最强的
两个人一律变成队长和冲刺手，全能型的 per100 从 104 掉到 25。
正确的做法是把分数换成 **z 分**——比的不是原始契合度，是「这个人在这个
角色上有多出众」，峰度的差异就此抵消。现在山地赛段是总成绩核心 44% /
爬坡手 42%，山顶终点 45% / 42%，大环赛总成绩核心 31 个对爬坡手 23 个：
**队长赢三周，爬坡手抢赛段**，两个角色终于各有各的活。

同一轮里还修了换血：`while len(roster) < 8` 那段用花名册长度去索引配方
（`recipe[len(roster) % len(recipe)]`），一支队丢了队长补进来的是工兵，
队长永远补不回来。改成按「缺什么角色」补。

**长赛季的世界水平已经稳住了，但过程绕了一圈。** 原来前 20 名平均总评
在 25 个赛季里摆动 4.5–6 分。我先按直觉加了微分项——用「24 岁以下那批人
的潜力」当前馈，看的不是今年的世界水平而是几年后的，理由很充分，结果
波动变成 5.0，没用；又把上下限从不对称的 (−0.20, +0.45) 改成对称，
理由同样充分（控制器能大幅加强青训却几乎不能削弱，只会往上冲过头），
结果 6.1，更糟。

真正管用的是**把增益调小**：除数从 22 改到 40，上下限收到 ±0.26。
波动降到 3.8 分，后 15 个赛季 3.5 分，曲线也从大起大落变成 82–85 的平缓
带子。这是控制理论的教科书答案而不是什么巧思——**这个回路有四五个赛季的
死区时间**（今年招的人五年后才进得了前二十），对死区时间大的系统，
增益够大就一定会以死区时间为周期摆动，加微分项治不了，只能把增益调小。
代价是回得慢，但不摆。

**途中爬坡/冲刺积分的通过顺序是近似的。** 快速结算不知道谁在突围里，
用终点名次加扰动代替。跑完整引擎时应当记录实际通过顺序 —— 引擎里有这个
数据，只是还没接出来。

**团体计时赛（TTT）还没做。** 需要队内轮转模型，比个人计时赛复杂。

**突围在「长下坡 + 长平路连接」的山地赛段上仍然偏强。** 陡坡上的优势已经
修掉了，但像「高山之王」这种山与山之间隔着二十公里下坡和平路的赛道，
突围仍能守住七分钟。剩下的成功率偏高。 现在突围能形成、差距落在真实的 4–6 分钟区间、
主集团会按一条真实的收网曲线追回来——但在部分种子下守住的概率高于现实中的
两三成。这是一个调参问题（`chase_boost` 的系数和 `breakaway_intensity`），
不是结构问题。

**关门率在山地赛段偏高。** 92% 完赛已在合理区间，但掉队的人碎成小集团后
各自为战，比真实的"关门集团抱团回家"更惨一些。

## 接下来的自然延伸

**一、强度曲线与追击控制器的联合重标定。** 这一轮把它当成一个参数拟合
问题正式做了一遍：三个旋钮（`INTENSITY_POINTS`、`CHASE_GAIN`、
`TOLERATED_SLOPE`）从代码里提到 `sim/tactics.py` 顶部，
`source/tune_peloton.py` 按网格扫，每个候选跑多颗种子取平均——不再看单次结果。

**结论是这三个旋钮里没有答案。** 33 组参数（终段/中段强度 × chase 增益 ×
容忍斜率）全部扫完，**没有一组同时满足两条判据**（平路中位差距 < 60 秒
且前八至少 5 个冲刺手）。最好的一组是终段 ×0.96、中段 ×0.97、
gain 0.85、slope 0.042：中位差距从 293 秒压到 **70 秒**，前八仍有 6 个
冲刺手——很近，但没过。完整结果在 `data/tune_peloton.json`。

**折线强度曲线这条路可以划掉了。** 之前记录的「折线把一分钟内完赛率从
42% 升到 68%」是在标定赛道上量的；换到单元测试那条 160 人的平路赛段上，
折线把这个比例从 31% **打到 5%**，前八的冲刺手从 8 个打到 1 个——
两条判据同时变坏。台阶的形状不是病根。

**下一步不该再动这三个旋钮。** 数据指向更底层的两处：掉队判定
（一个人多大的功率缺口、持续多久才算被甩掉）和跟车收益本身
（集团里第 80 位的人到底省下多少）。真实的平路赛段有一百多人同时过线，
不是因为领骑放松，是因为跟在集团里几乎不花钱。

这条现在是 `test_sim.py` 里的**已知缺口**：断言一个字没改，
测试照跑照打印实测值，只是不让 CI 红着——阈值绝不放松，
那等于把问题藏起来。

**二、全能型的 per100 只有 30**（曾经 104）。世巡赛队少了一个爬坡手坑位、
角色重排改成 z 分之后人口结构变了。他仍然守着计时赛（25%）和石板路（30%）
两块地盘，但需要一轮专门复查。

**三、~~途中积分的真实通过顺序~~ —— 已经做完了。** 之前这里写的是
「引擎里有这个数据，只是没接出来」，**那句话是错的**——去接才发现
`sim/race.py` 根本不记录谁在什么时候越过 KOM 点。现在记了：用「上一步在点
之前、这一步在点之后」判定，顺序天然就是真实的通过顺序。

效果一眼能看出来。同一个山地赛段，前两个爬坡点的越点前四名，
终点名次是 5 / 16 / 22 / 23——**那是突围里的人，拿完积分之后被追回去了**；
最后一个爬坡点的越点顺序则是 1 / 2 / 3 / 4，和终点一致。爬坡王衫的整个
玩法就建立在这个差别上，而「终点名次加扰动」的近似完全看不见它。

快速结算给不出这个数据（它没有「比赛过程」这个概念），仍然用近似。
**两条路径在这一项上不一致，这是有意接受的**：途中积分不影响总成绩，
为它给快速结算编一套假的过程，代价远大于收益。玩家亲自看的那场比赛
拿到的是真数据。

加这个记录一度把 `verify_incidents` 拖到超时——每一步扫「所有点 × 所有
车手」是 3×160×18000 次比较。加了两道闸（已全部通过的点不再看、
还没有人到的点直接跳过）之后恢复正常。
