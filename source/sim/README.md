# 核心比赛模拟引擎

《模拟自行车队经理》的比赛内核。纯 Python 标准库，不依赖任何游戏引擎，
Unity / Godot / Web 前端都可以把它当成一个数值服务调用。

```python
from sim import Race, build_peloton, mountain_stage, format_gap

riders = build_peloton(n_teams=20)             # 160 名车手
result = Race(mountain_stage(), riders, seed=42).run()

for place, s, gap in result.standings()[:10]:
    print(place, s.rider.name, format_gap(gap))
```

一场 160 人的赛段在普通笔记本上约 15-25 秒算完。

---

## 为什么这样设计

管理类游戏最容易踩的坑，是把比赛写成一张加权随机表：属性高的人抽中的
概率大一些，然后编个理由解释结果。这种做法前十小时可玩，之后玩家就会
发现自己不是在带队比赛，而是在刷一个隐藏的骰子。

这个引擎里没有胜负判定。它只做四件事，每秒循环一次：

1. **聚集团** — 按赛道位置把车手聚成集团，算出每人的破风系数
2. **定速度** — 集团速度 = 一个"平均能力的人顶着风"以某强度骑的速度
3. **反解功率** — 每人算出跟住这个速度要踩多少瓦，付不起的自动掉队
4. **扣账** — 超过临界功率就烧无氧储备，低于就回充

名次是这个循环跑完之后的副产品。掉队、追回、爆掉、终点绝杀，全部是
涌现出来的，没有一行脚本写"某某应该在此处获胜"。

## 三个核心模型

### 功率-速度（`physics.py`）

标准的自行车功率方程，重力 + 滚阻 + 风阻，按牛顿第二定律逐步积分而不是
直接取平衡速度。这样"拉开差距需要时间"这件事是自然发生的，不需要额外
规则去补。空气密度按国际标准大气随海拔变化——2000 米山顶的密度只有海平面
的 80%，这会让高山下坡明显更快。

### 双能量池（`energy.py`）

不是一根体力条，而是两个池子：

- **CP（临界功率）** — 理论上可以无限持续的有氧水平
- **W′（无氧储备）** — 有限的焦耳数，超过 CP 就消耗，低于 CP 就缓慢回充

这一个改动带来了管理游戏最需要的全部质感：车手可以短时间爆发去追突围，
但"火柴"数量有限；山区反复变速比匀速消耗大得多；躲在集团里省下的每一瓦
都直接换算成终点前还剩多少子弹。回充速度用 Skiba 的时间常数模型，
骑得越轻松回得越快。

另外 CP 本身会随全程累计做功而衰减——四小时后的 CP 比出发时低 8-15%，
这是决定谁能在最后一座山扛住的核心变量，也是"耐力"属性的主要出口。

### 集团与破风（`pack.py`）

跟在别人后面能省 25-45% 的功率，这是自行车比赛全部战术张力的来源。

集团速度由"一个平均能力的车手顶着风"决定，躲在后面的人按自己的破风系数
少付。这一条自动解释了两件事：平路上大集团谁都跟得住（风阻占比高，
跟车省得多），而爬坡时集团必然碎掉（坡上功率主要用于对抗重力，跟车省不下来）。

还有一个容易被忽略但极其关键的量：**集团在路上并排几个人**。宽路巡航时
5-6 人一排，160 人的集团全长只有几十米，冲刺手离最前面不过十来米；一旦
上坡或刮侧风，队形拉成单列长龙，同样的排位就变成落后几百米。终点前的
一切成败都建立在这个几何上。

## 车手属性

九项 0-100，50 是职业队平均，100 是世界顶级。`rider.py` 里的
`derive_params()` 把它们翻译成物理参数——所有魔法数字都集中在那一个函数里，
调平衡只需要改那里。

| 属性 | 作用出口 |
|---|---|
| 平路 flat | 平路临界功率 |
| 爬坡 climbing | 陡坡临界功率（坡度 6% 以上完全按它结算） |
| 冲刺 sprint | 峰值功率 + 无氧储备容量 |
| 计时 time_trial | 迎风面积（气动姿势） |
| 下坡 descending | 下坡速度上限、弯道损失 |
| 耐力 endurance | 抗 CP 衰减，长赛段后段的保持 |
| 恢复 recovery | W′ 回充速度 |
| 占位 positioning | 跟车质量、集团里挪位置的速度、冲刺时能不能找到好轮子 |
| 意志 resilience | 储备见底后还能维持的功率比例 |

平路和爬坡是**两条独立的 CP**，按坡度插值。好处是"爬坡属性"对策划和玩家
都有直白的含义——它就是你在坡上的持续功率，而不是一个说不清作用在哪的
隐藏加成。冲刺手爬坡属性低，上坡时 CP 自动打折，不需要额外写惩罚规则。

## 战术

`tactics.py` 里每个车手每秒只输出两个量：目标功率，和要不要在前面干活。
不允许直接改位置或名次。

- **配速曲线** — 开场 15 分钟抢突围最凶，突围放走后集团放松，最后 30 公里
  再次拉高。这条曲线直接决定赛段的观赏节奏。
- **筛选系数** — 集团配速相对"集团平均 CP"的倍率，随剩余距离递增。
  这是全引擎最重要的旋钮，决定什么时候开始成批掉人。
  里面有一条阻尼：集团越小配速越保守，否则"弱者掉队 → 均值 CP 抬高 →
  配速更狠 → 掉得更多"会形成恶性循环，把山顶终点变成碾压。
- **攻击** — 按每秒概率触发而非硬阈值，所以同样的阵容跑两次不会一样。
  爬坡手只在够陡的坡上、离终点够近时才动手。
- **冲刺列车** — 领骑员把队长拉到 400 米处交棒退出，自己不争名次。
- **掉队自保** — 火柴烧光就降到有氧水平；缓过一口气会重新参与比赛，
  否则一次掉队等于判死刑。

## 赛道

`course.py`。赛道是一串分段（长度、坡度、路面、风），俯视地图和海拔剖面
都从这份数据程序化绘制——美术清单里明确这两项不出图。

内置四种赛段生成器：`flat_stage()`、`mountain_stage()`、`itt_stage()`、
`cobbled_stage()`。个人计时赛走独立代码路径（逐个发车、无集团无跟车），
硬套主循环只会得到"一群人抱团骑计时赛"这种荒唐结果。

## 验证

```bash
python3 source/tests/test_sim.py          # 33 项单元测试
python3 source/calibrate.py               # 与真实赛事数据对照

```

`calibrate.py` 把每个可观测量和公开的职业赛数据区间并排打出来。
当前状态：

| 项目 | 引擎输出 | 现实参考 |
|---|---|---|
| 13.8km @ 8.1% 单人爬坡 | 40.3 分 / 1666 m/h | 37–45 分 / 1350–1750 m/h |
| 180km 平路赛段均速 | 40.3 km/h | 40–45 |
| 165km / 4378m 山地赛段均速 | 31.2 km/h | 29–34 |
| 38km 个人计时赛均速 | 45.4 km/h | 44–53 |

| 山地赛段冠军平均功率 | 4.00 W/kg | 3.2–4.3 |

行为层面：平路赛段前八名有七个是冲刺手、全场 80% 在冠军后 11 秒内过线；
山地赛段前八全是爬坡手和总成绩核心、中位差距 16 分钟；计时赛前八是
平路手和全能手，没有集团一起过线的现象。这些都不是写死的，是跑出来的。

## 接下来可以接的东西

引擎本身是完整的，下面这些是它的自然延伸，互相独立，可以按需要挑：

- **团体计时赛（TTT）** — 需要队内轮转模型，比 ITT 复杂
- **积分与分类** — KOM 点、冲刺点已经在 `Course.koms` 里留好数据结构
- **多日赛总成绩** — 把逐日 `finish_time` 累加，加上时间补偿规则
- **摔车与机械故障** — 建议挂在 `technical`、路面、雨天条件上，而不是纯随机
- **赛前指令** — 玩家给车手设"保护队长 / 自由发挥 / 抢突围"，接进 `tactics.decide`
- **回放数据** — 主循环里逐秒记录位置，前端就能画实时竞速卷轴
